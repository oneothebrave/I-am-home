## 发布防错入口

在项目目录执行：

```text
npm run check:release
npm run check:all
```

前者只读检查工程；后者依次执行防错、类型检查、全部测试和 iOS JavaScript 打包。`npm run bundle:ios` 的前置步骤和现有 GitHub Actions 都接入了检查。脚本根据自身路径定位项目，不依赖调用时的目录或 Windows 盘符。

检查失败返回非零退出码，没有跳过检查或自动打开短信开关的参数。直接运行原始打包工具、修改构建设置或使用其他流程仍可能绕过它，因此最终安装包还必须人工核验。

## 时间行为与修复

仍维持单段、同日守护时间，开始时间包含、结束时间不包含；不新增跨夜或多段规则。

- 守护时段按手机当前本地时间判断；位置年龄和 30 天保存期按绝对毫秒差计算，不用显示出来的小时数字相减。
- 在独立 Node 进程中覆盖 UTC、上海、纽约、柏林、加德满都和阿皮亚。包含 45 分钟的非整数小时偏移、跨日、运行中切换时区，以及纽约/柏林夏令时跳时和重复小时。不修改电脑系统时钟或时区。
- 复现并修正“未来 10 秒的确认安全/恢复记录提前解除当前告警”。未来事件保留在历史中，但未到其时间时不参与状态回放；不把未来的恢复描述为已经确认。
- 当历史包含晚于当前时间超过 5 秒的记录时，状态页和诊断提示检查系统日期与时间，不据此显示新的安全结论。现有可回放风险仍显示风险。此提示不会停止原生守护、修改规则或触发外发。
- 新事件进入、App 回到前台时立即更新展示用时钟，避免拿上一次 30 秒刷新的时间误判新记录。
- 复现并修正时钟回拨后，旧时钟下的大批未来采样挤掉新采样的问题。当前普通历史和未来记录分开整理。
- 无效时间值不会触发历史删除；无效/跨夜/相同端点的时间配置不视为有效守护时段。

### 时间异常期间的保留例外

正常时间范围内仍保留 30 天、最多 2,000 条普通记录及既有活动告警证据。未来记录暂单独保留最近 2,000 条，另保留未来的非原始位置事件和第一条未来位置样本，避免丢失当前告警稍后的恢复证据或旧版位置恢复依据。

因此时间异常期间总量可能超过 2,000 条，未来状态变化记录也不受普通上限约束。时间恢复后，在下一次整理中回归普通规则；分页仍最多渲染 40 条。这是保守保留，不是永久备份或修改原始时间戳。

没有可信服务器时间时，不能区分“大幅前拨系统时间”和“真的很久没有使用 App”。前拨后普通过期记录仍可能按 30 天规则移除，已删除记录不能因随后回拨恢复；活动告警证据仍受到保护。不承诺任意调时都能无损重建原始先后顺序。
