## 高优先级发现

### R01 · P1 · 新的低电量事件会降级未解除的 SOS

位置：[riskEngine.ts:18](E:/CHECK/src/domain/riskEngine.ts:18)、[riskEngine.ts:44](E:/CHECK/src/domain/riskEngine.ts:44)、[riskEngine.ts:70](E:/CHECK/src/domain/riskEngine.ts:70)。

风险引擎以数组最后一条事件决定整个状态。`SOS_SENT -> LOW_BATTERY` 会从 `emergency` 变成 `attention`，即使本人没有解除求助；最后一条为未在分支中处理的事件还会默认进入 `safe`。这会丢失正在处理的告警。审查用例已复现低电量降级。

建议：用事件归约维护正在处理的告警及解除原因，给主动 SOS 定义明确的解除动作。电量和位置更新只更新相关信号，不能自动覆盖未解除的求助。没有可信信号时需要“未知/监测不可用”等状态，不能直接显示安全。

### R02 · P1 · 主动求助没有独立的升级入口

位置：[escalation.ts:32](E:/CHECK/src/domain/escalation.ts:32)、[escalation.ts:40](E:/CHECK/src/domain/escalation.ts:40)、[App.tsx:127](E:/CHECK/App.tsx:127)。

在概览点击“我没事”，再点击“求助”，首页进入异常，但升级状态为 `idle`，没有下一步。原因是 `hasActiveRisk` 只认四类被动风险，不包含 `SOS_SENT`。如果保留先前被动风险再求助，则又进入 `self_prompt`，要求已经主动求助的人再次确认。两条路径均已复现。

建议：SOS 独立开启告警，直接进入联系人通知阶段；本人确认等待只适用于被动风险。本项讨论的是原型状态机，不代表当前已经具备真实推送能力。

### R03 · P1 · 按通知条数推算接收人会漏通知

位置：[escalation.ts:34](E:/CHECK/src/domain/escalation.ts:34)、[types.ts:34](E:/CHECK/src/domain/types.ts:34)。

当前通过 `FAMILY_NOTIFIED` 的条数截取当前联系人数组，没有保存实际通知的 `contactId`。通知阿明后删除阿明，剩下的小兰会被当作已经通知，流程直接完成。重复收到同一条通知事件也会消耗下一位名额。两种情况均已复现；名单删除路径在现有页面可操作。

建议：通知事件包含 `incidentId`、`contactId`、稳定事件 ID 和发送结果，按接收人记录状态并去重。应明确处理中修改名单的规则，区分待发送、发送成功、发送失败和家人已确认。

### R05 · P1 · 存储降级与错误处理不完整

位置：[guardianStorage.ts:45](E:/CHECK/src/storage/guardianStorage.ts:45)、[guardianStorage.ts:52](E:/CHECK/src/storage/guardianStorage.ts:52)、[App.tsx:77](E:/CHECK/App.tsx:77)、[App.tsx:101](E:/CHECK/App.tsx:101)。

主存储失败时，`save/clear` 的 `finally` 会更新内存，但原始异常继续向上传播。App 只有 `.then()`，没有错误分支，导致保存状态不更新；重置时即使内存已清空，页面也不会重置。另一个独立问题是成功读取的主存储状态没有同步给内存副本：先成功加载真实配置，再出现临时读失败，会读回默认演示联系人。三个场景均已复现。

建议：返回可区分“已持久保存”“仅内存保存”“读取/保存失败”的结果，页面处理错误和重试。成功读取后同步内存副本；冷启动读取失败不得冒充“无历史数据”并允许覆盖原有配置。不要用吞掉所有异常来制造保存成功的表象。

### R06 · P1 · 启动读取会覆盖读取期间的用户操作

位置：[App.tsx:61](E:/CHECK/App.tsx:61)、[App.tsx:83](E:/CHECK/App.tsx:83)、[App.tsx:91](E:/CHECK/App.tsx:91)。

加载本地数据时，页面按钮与表单已经可操作；`isHydrated` 只用于文字展示。用户在慢读取期间新增联系人或报平安后，加载回调仍会无条件替换 `config/localEvents`，覆盖较新的页面状态。这是根据调用路径确认的竞态，本次没有运行 React Native 组件级复现。

此外，两个 React state updater 内直接异步写存储，并交叉使用闭包中的另一份状态，没有集中协调或写入顺序控制。updater 被重试或配置与事件同时变更时，可能写入重复或过期的完整快照。后一项需要组件级延迟测试进一步验证，不能把审查用的纯函数测试视为已覆盖。

建议：集中管理配置和事件，使用纯 reducer；加载前阻止配置提交或排队合并操作。求助入口应单独设计，不能因为加载而丢失。持久化移到专门协调层，明确保存顺序、重置与加载的关系。

### R10 · P1 · 原生定位回调被无条件包装成新鲜移动信号

位置：[GuardianLocationService.swift:52](E:/CHECK/ios/GuardianCore/GuardianLocationService.swift:52)。

代码不检查 `CLLocation.timestamp`、`horizontalAccuracy` 或与上一位置的实际距离，所有回调都生成 `MOTION_DETECTED`，并把事件时间改为 `Date()`。缓存位置或不可信定位因此可能成为“刚刚移动”的安全信号；风险引擎又会用它解除关注乃至求助。

Apple 明确说明定位回调可能包含缓存数据，应检查位置时间。参见 [Apple 定位数据处理文档](https://developer.apple.com/library/archive/documentation/UserExperience/Conceptual/LocationAwarenessPG/CoreLocation/CoreLocation.html)。本项是结合系统文档的静态发现，尚未真机验证。

建议：保留测量时间与接收时间，先检查时效、精度和移动可信度，再生成领域事件；原始定位更新与可信移动应为不同事件。是否解除主动求助必须有单独规则。

### R11 · P1 · 原生事件没有持久队列，重建后围栏映射也会丢失

位置：[GuardianNativeModule.swift:9](E:/CHECK/ios/GuardianCore/GuardianNativeModule.swift:9)、[GuardianLocationService.swift:6](E:/CHECK/ios/GuardianCore/GuardianLocationService.swift:6)、[GuardianLocationService.swift:40](E:/CHECK/ios/GuardianCore/GuardianLocationService.swift:40)。

事件只通过 `sendEvent` 发给 JS，没有本地持久化、待消费队列和确认机制。已安装 RN 的 [RCTEventEmitter.m:63](E:/CHECK/node_modules/react-native/React/Modules/RCTEventEmitter.m:63) 在没有监听者时不会交付事件。即使后续补上页面订阅，JS 尚未订阅时到来的后台事件仍可能丢失。

`geofencesById` 只保存在进程内存，服务重建后为空，回调会在 `guard` 处直接返回。Apple 的后台重新启动流程要求重建定位服务，参见 [Apple 定位服务启动说明](https://developer.apple.com/library/archive/documentation/UserExperience/Conceptual/LocationAwarenessPG/CoreLocation/CoreLocation.html)。这是原生草案接入前需要解决的问题，不是已在真机复现的故障。

建议：原生层先保存配置和事件，再尝试推送给 JS；JS 消费后确认，支持重放和去重。通过系统位置事件启动时恢复配置及服务。不能仅依靠 RN 页面挂载来恢复后台守护。

### R09 · P2 · 持久化事件没有统一日期语义

位置：[App.tsx:109](E:/CHECK/App.tsx:109)、[time.ts:1](E:/CHECK/src/utils/time.ts:1)、[riskEngine.ts:93](E:/CHECK/src/domain/riskEngine.ts:93)、[TimelineScreen.tsx:58](E:/CHECK/src/screens/TimelineScreen.tsx:58)。

本地事件只保存 `HH:mm`，Swift 事件却保存 ISO 时间。事件持久化后跨天仍全部显示在“今天发生了什么”，最后安全信号也始终加“今天”。接入 Swift 后，ISO 字符串又会直接显示在为短时钟文本设计的位置。日期信息丢失后无法正确比较超时、分组或判断信号是否过期。

建议：事件统一存储完整 UTC 时间，界面按本地日期格式化；明确事件顺序、重复事件处理与信号时效。按日期筛选展示，不等于在跨天时自动清除未解除告警。

## 重构建议与顺序

保留现有 React Native + Swift 方向，以及 `screens/domain/storage/native` 目录职责。当前没有必要为拆分文件而继续增加层级，也没有证据表明需要立刻换数据库。

1. 先为 R01/R02/R03 建立统一告警状态机。事件保持为事实，领域状态记录当前告警、信号时间和通知进度，页面与文案从它派生。
2. 收敛 App 状态与持久化协调。以一个应用状态处理配置和事件，使用纯 reducer；由专门 hook/协调器负责加载、保存、失败和重试，消除 state updater 中的 I/O。
3. 固化事件和存储 schema。统一时间、稳定 ID、告警 ID、联系人 ID、围栏 ID；集中做边界校验与版本迁移，把演示数据移到明确的演示入口。
4. 修复原生事件可靠性后接桥。原生保存配置与事件队列，恢复监听，提供权限实态和消费确认；后台判断与通知执行不能依赖页面一直在运行。
5. 将审查用例转入正式测试体系，增加组件、时间和故障注入测试，并让 CI 至少执行类型检查、规则/存储测试和 JS bundle。随后在 Mac 上补 Swift 和真机验证。

构建配置也应整理：`react-native` 为 0.82.0，而 Babel/Metro 配套为 0.87.0。当前 Node 24 打包已通过，不能仅因版本不同就断言无法运行；但项目声明 Node `>=20`，已安装 Metro 配置却要求 `^22.13.0 || ^24.3.0 || >=26.0.0`，环境要求确实不一致。应统一受支持的工具链并准确声明 Node 范围。

需要确定的产品规则：被动移动能解除哪些告警、主动 SOS 的解除方式、处理中修改联系人如何生效、通知“发送成功”与“家人确认”如何区分。当前建议是主动求助必须显式解除，联系人通知按实际接收人追踪。这些决策应在实施状态机时写入验收用例。
