# 本地状态与持久化

页面通过 `guardianStore` 发出操作，`guardianReducer` 只计算新状态。`useGuardian` 使用 React 的订阅接口读取状态；React state updater 内不再执行存储 I/O。

## 数据边界

`guardianSchema.ts` 定义 v2 状态：`schemaVersion`、`config`、`localEvents`、`isGuardianOn`、`mode`、`updatedAt`。演示事件只在明确创建演示状态时生成一次，不在每次渲染时拼入固定事件。

`validation.ts` 校验配置、事件、坐标、号码、时间、重复 ID 和能力上限。合法 JSON 不代表合法应用状态。未知版本和损坏数据会阻止加载，页面可重试，不能自动用默认配置覆盖旧数据。

## 迁移

保留原 key `@daojia_shuo_yisheng/guardian_state_v1`，其内容升级为 v2，避免遗漏旧安装数据。旧记录的 `HH:mm` 以 `updatedAt` 为上界，从后往前推断最近可能的本地日期，遇到跨午夜则回退一天。

旧格式没有保存实际日期，因此这只是有说明的兼容迁移，不能保证恢复原始日期。旧通知没有接收人或告警 ID 时不猜测身份，也不会计入新的通知进度。v2 新事件必须有完整时间。

## 加载和保存

- 加载前禁止配置提交，求助/报平安先放入待合并操作队列；读取成功后合并到真正载入的数据，不覆盖较新的操作。
- 读取失败保留待处理操作，重试成功前不写默认状态到磁盘。
- 仓库将操作串行化，写入前捕获已校验的副本；协调器合并连续修改，`flush()` 等待所有较新的修订处理完毕。
- 重置也是一次完整状态替换，与其他修改使用同一保存队列；不会和旧写入交错恢复旧配置。
- 主存储读取成功时同步内存副本。冷启动读取失败且没有可信副本时抛错。
- 主存储写入失败后可在内存继续，页面明确显示“仅保存在内存”；未落盘修改不会被恢复后的旧主存储覆盖。
- `retry()` 会重试当前最新状态。保存时间只在真正持久保存成功时更新。

## 原生事件消费

设备模式通过 `guardianEventSync` 先订阅再拉取原生队列。只有 `importEvents` 返回真正持久保存成功，才确认相应事件 ID。内存降级和写入失败都不能确认消费；确认失败后的重复交付由事件 ID 去重。重新进入前台或手动重试时会再次拉取。

默认入口仍为演示模式。设备模式是为 iOS 接入保留的数据/消费接口，尚未开放为已完成的真实守护流程。
